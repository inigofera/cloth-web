## 1. Executive summary

**cloth-web is a personal wardrobe manager**: clothing items with photos, an outfit
calendar logger, a 19-widget analytics dashboard, generic table CRUD, AI virtual
try-on (Google Gemini BYOK or a self-hosted Qwen-Image-2.1-Turbo worker), and optional
Discord outfit-log import. Auth is Supabase JWTs; data lives in Supabase Postgres +
Storage.

**Verdict:** the *features* of a 1.0 are ~90% present and the implementation quality is
high (consistent per-user scoping, hardened upload pipeline, transactional outfit
operations, good unit tests on both stacks, a passing CI gate). The remaining ~10% is
almost entirely **deployment, schema reproducibility, verification, and release
hygiene** — none of it requires new architecture. Half of the remaining work is already
specified in the repo's own (currently untracked) `docs/home-infra-plan.md`.

**Three blockers, in short:**

1. The base database schema (7 core tables) was created manually in the Supabase
   project and **cannot be recreated from `git clone`** — the repo's migrations start
   six weeks later and only add constraints. Fresh instances are not reproducible.
2. The deployment plan (GitHub Pages + Cloudflare Tunnel + GHCR + compose) exists only
   as a document: no Dockerfile, no CI deploy jobs, **no CORS support in the backend**,
   no `/healthz`, and no configurable API base URL in the frontend.
3. Nothing is versioned for release: `0.1.0` in both manifests, no git tags, no
   CHANGELOG, no LICENSE, and a dirty working tree.

**Critical path:** base-schema migration → security/ops hardening → execute
`docs/home-infra-plan.md` → tag `v1.0.0`. Estimated **1.5–2.5 weeks** of focused work,
with the deployment phase (~2 days, per the plan's own estimate) as the longest single
stretch and the only one with external dependencies (Squarespace DNS, Cloudflare
account, the `inibaby` NUC).

## 3. Architecture overview

```
Browser (Vue 3 SPA)
   │  Supabase JS: auth only (signIn/signUp/OAuth, session)
   │  fetch:  /api/*  ── same-origin today; cross-origin after the plan lands
   │
Backend (Rust/Axum, :3000, single process)
   │  JWT verify (HS256 + SUPABASE_JWT_SECRET, role=authenticated)
   │  generic table CRUD  ── per-table SQL rendered once from a startup schema snapshot
   │  outfits (transactional, wear counts)
   │  settings (AES-256-GCM encrypted API key)
   │  upload → Supabase Storage (service-role key)
   │  /files proxy (per-user ownership gate, thumbnail bucketing, LRU cache)
   │  try-on orchestration → Gemini REST  or  local Qwen FastAPI worker
   │  Discord bot API (import + link codes)
   │
Supabase (Postgres + Storage)   local_inference (FastAPI + sd-cli, optional)
```

Data model (as used by the code; authoritative source is the live DB — see §5.1):
`clothing-items` (user-scoped), `outfits` (user-scoped) ↔ `outfit-items` (join),
`brands` (user_id nullable: shared or owned), `clothing-categories`,
`clothing-subcategories`, `colors` (text-slug keyed), `user-settings`
(user_id PK, the only table with RLS). Tables with a `user_id` column are scoped to the
authenticated user in the generic CRUD layer; tables without one are shared reference
data (read-only through the generic API). `user-settings` is blocked from the generic
API entirely.

## 4. Strengths — what is already at 1.0 quality

Do not re-litigate these; they are done well and are evidenced by tests:

1. **Consistent per-user scoping.** JWT extractor (`src/auth.rs`) validates HS256,
   audience `authenticated`, and role; `user_id` is force-overwritten on every generic
   insert (`src/routes.rs:224`); `image_path` values are validated to stay inside the
   user's own storage folder (`validate_image_path`, with traversal tests);
   `/files/*path` re-checks ownership (`object_path_within_user`); storage keys are
   `users/{uuid}/{random-uuid}-{name}` so collisions across or within users are
   impossible.
2. **Hardened upload pipeline** (`src/upload.rs` + `upload_file`): 10 MiB cap,
   filename sanitization (allowlist `[A-Za-z0-9-_]`, extension allowlist),
   magic-byte sniffing (rejects renamed executables), EXIF auto-orientation, 1600px
   Lanczos3 downscale, progressive JPEG re-encode, thumbnail derivatives (96/480px)
   written at upload time, self-healing thumbnails for legacy images.
3. **Transactional outfit operations.** Create inserts outfit + links items in one
   statement + increments wear counts, all in one transaction, and reads the created
   row back *inside* the transaction; delete decrements (floored at 0), removes links,
   deletes — one transaction. No window where an outfit exists without its items.
4. **SSRF validation for the local inference URL** (`validate_local_qwen_url`):
   blocks link-local/metadata addresses (`169.254.*`), reserved ports 3000/5432,
   loopback-only by default, RFC-1918 LAN only behind `ALLOW_LAN_INFERENCE_URLS`.
5. **Secrets handling.** API keys encrypted at rest (AES-256-GCM, random 12-byte nonce
   per write), never returned to the client (only a `...last4` hint); Supabase
   service-role key server-side only; JWT secret never in the frontend.
6. **Honest pagination.** `COUNT(*) OVER ()` folded into list queries;
   `X-Total-Count` header; stable page ordering (`created_at DESC, id ASC`);
   the client walks all pages (`fetchAllPages`) with a 50k runaway guard.
7. **Performance work already done and commented:** schema read once at startup
   (`SchemaCache`), per-table SQL rendered once, thumbnails as byte-copies, bounded
   LRU image cache (512 entries / 24 MiB), outfit rows carry item *ids* not copied
   item objects.
8. **Frontend quality:** real unit tests (14 spec files: dates/timezone, error
   classification, routing, sanitizers, undo manager, wardrobe store, picker recency,
   insights metrics, layout persistence, widget smoke); a11y work (APG listbox
   patterns, keyboard widget reordering, confirmations + undo for destructive
   actions); KeepAlive tab preservation; deep-linkable URLs; 401→refresh→retry in
   the fetch layer; Chart.js code-split into the Insights tab.
9. **CI gate is real:** `cargo fmt --check`, `clippy -D warnings`, `cargo test`,
   release build, artifact upload; frontend `tsc --noEmit`, Vitest, Vite build.

## 5. Blockers

### 5.1 The base schema is not in the repo

**Finding.** `supabase/migrations/` contains only:

| Migration | What it does |
|-----------|--------------|
| `20260922000000_constrain_clothing_item_select_fields.sql` | CHECK constraints on **existing** `clothing-items.origin` / `laundry_impact` |
| `20261018000000_create_user_settings.sql` | Creates `user-settings` + its only RLS policy |
| `20261018000001_add_tryon_provider_columns.sql` | try-on provider / local Qwen URL columns |
| `20261026000000_add_discord_integration.sql` | Discord link columns on `user-settings` |
| `20261105000000_index_user_scoped_tables.sql` | Generic `(user_id)` / `(user_id, created_at DESC)` index pass |

The core tables — `clothing-items`, `outfits`, `outfit-items`, `brands`,
`clothing-categories`, `clothing-subcategories`, `colors` — were created manually in
the live Supabase project. Consequences:

- A fresh Supabase project (new machine, second instance, re-creation) **cannot be
  bootstrapped from the repo**.
- The `20260922` migration will *fail* on a fresh project (it references
  `clothing-items` before anything creates it).
- No RLS exists on any user-scoped table (only `user-settings` has a policy). The
  backend's direct Postgres connection (presumably service-role) bypasses RLS anyway,
  and the frontend never queries Postgres directly (only `supabase.auth`), so this is
  defense-in-depth — but it should exist for a 1.0.
- There is no migration ledger/runner anywhere in the repo; the README says "apply
  them when setting up the Supabase project" (manually).

**Work.**

1. Reconstruct the live schema: run
   `SELECT table_name, column_name, data_type, is_nullable, column_default FROM information_schema.columns WHERE table_schema='public' ORDER BY table_name, ordinal_position;`
   plus `pg_constraint` / `pg_index` dumps on the live project, and write
   `supabase/migrations/20251001000000_base_schema.sql` that creates the seven tables
   byte-faithfully *before* the existing migrations. (Date prefix must sort first —
   Supabase/migration runners order by filename.)
2. From code usage, the expected shapes are:
   - `colors(id text PK, hex_value text)` — id is a lowercased slug
     (`create_color` lowercases; `ColorRef.id: String`).
   - `brands(id uuid PK, user_id uuid NULL, name text)` — `discord.rs` queries
     `WHERE user_id = $1 OR user_id IS NULL`, so brands are shared-or-owned.
   - `clothing-categories(id integer PK identity, name text)`.
   - `clothing-subcategories(id integer PK identity, name text, category_id integer FK)`.
   - `clothing-items(id uuid PK, user_id uuid, name text, brand_id uuid,
     category_id integer, subcategory_id integer, color_id text,
     purchase_price numeric, owned_since date, origin text, laundry_impact text,
     repairable boolean, notes text, image_path text, is_active boolean,
     wear_count integer, created_at timestamptz, updated_at timestamptz)`
     (field list from `frontend/src/api/types.ts` `ClothingItem` + `discord.rs`
     insert + migration 1 constraints).
   - `outfits(id uuid PK, user_id uuid, date timestamptz, notes text, image_path text,
     is_active boolean, created_at, updated_at)` — `date` is bound `$2::timestamptz`
     and rendered `to_char(o.date,'YYYY-MM-DD')`.
   - `outfit-items(outfit_id uuid FK→outfits, clothing_item_id uuid FK→clothing-items,
     unique pair)` — dedupe logic assumes uniqueness.
3. Add RLS to every user-scoped table (`FOR ALL USING (auth.uid() = user_id) WITH
   CHECK (auth.uid() = user_id)`; brands: `user_id IS NULL OR auth.uid() = user_id`).
4. Add the migration ledger + runner per `docs/home-infra-plan.md` §1.6
   (`schema_migrations` table; seed it with already-applied names on first run).
5. Make the CI integration test (§8.1) apply the *full* migration chain against a
   fresh Postgres — this is what proves the chain works end to end.

public; the rest are hardening.

### 6.1 JWTs are embedded in image URLs (high)

`frontend/src/api/client.ts:55` — `imageUrl()` appends
`params.set('token', accessToken)` to every `/files/...` request, and
`src/auth.rs:56` (`token_from_query`) accepts `token` from the query string. Once the
site is public, live JWTs will appear in access logs (the tunnel/nginx request line),
browser history, and potentially `Referer` headers on cross-origin navigation.

**Fix options (pick one):**
- Short-lived signed image URLs: `/files/*path?sig=...&exp=...` where the backend
  signs (HMAC with the settings key or a dedicated key) a `path + user_id + expiry`;
  the query token is a 10-minute HMAC, not the JWT.
- Or: a per-user HTTP cookie set by a tiny `/files/login` endpoint (Supabase
  refresh-token flow), used only for the `/files` origin.
- Minimum viable: keep the JWT query param but configure the tunnel/nginx
  `log_format` to strip the query string, and add `Referrer-Policy: no-referrer`.

### 6.2 Discord link-code flow (medium)

`src/routes.rs:1030` — the 6-digit code is generated with
`rand::thread_rng().gen_range(100000..999999)`:
- `thread_rng` is not a CSPRNG (irrelevant for 15-minute codes in practice, but the
  right tool is one import away — `getrandom` / `OsRng`; also unblocks moving off
  deprecated `rand 0.8`).
- **No attempt limiting.** `sync_discord_for_user` answers `!link <bad code>` with a
  ❌ and moves on; there is no per-user throttle, so a Discord-side attacker can
  brute-force ~900k possibilities over time against the 15-minute window, and each
  wrong attempt gets a confirmation reply (oracle).
- Codes are stored as plain text in `user-settings` and compared with an exact-match
  `UPDATE ... WHERE discord_link_code = $2 AND discord_link_expires_at > now()`.

**Fix:** generate with `OsRng`; track failed attempts (e.g., a column
`discord_link_fail_count` + `discord_link_locked_until`, or a small
`discord-link-attempts` table); lock a Discord user out for 1 hour after 5 failures;
only reveal code validity after the lockout check.

### 6.3 Shared reference data is globally writable (medium, multi-user only)

`POST /colors`, `/clothing-categories`, `/clothing-subcategories`
(`src/routes.rs:391–499`) insert into **unscoped** tables. Any authenticated user can
add entries that appear in every user's wardrobe form. The generic API correctly
forbids writes on shared tables (`"table is shared reference data"`), so the exposure
is add-only via these three dedicated endpoints.

**Fix:** decide the multi-user story (§9.5). Single-user: document it. Multi-user:
either scope reference data per user (add `user_id`, dedupe on create, merge existing
global rows into per-user rows) or restrict creation to the account that owns the
project.

### 6.4 JWT validation is secret + role only (low-medium)

`src/auth.rs:38-47` sets audience and checks role but does **not** validate `iss`.
Any Supabase project whose JWT secret happens to match would mint valid tokens. The
secret is per-project and random, so this is low risk; fixing is ~3 lines:
`validation.validate_iss = Some(true)` + `validation.issuer = SUPABASE_URL`.

### 6.5 DDL executed at startup in application code (low-medium)

`src/db.rs:16-25` — `connect_db()` runs
`ALTER TABLE public."user-settings" ADD COLUMN IF NOT EXISTS discord_user_id ...`
on every boot. This duplicates migration `20261026000000` and means production code
writes DDL. Move it into the migration chain and delete it from `connect_db()`.

### 6.6 No rate limiting (low, rises with exposure)

`/upload` (25 MiB body cap, 10 MiB file cap), `/outfits/generate-preview`
(Gemini paid API / ~5-min GPU renders), and the generic CRUD endpoints have no
per-user limits. Acceptable for one known user behind a tunnel; add simple per-user
sliding-window counters (in-process `HashMap` is enough at this scale) for upload and
try-on before opening the domain to the world.

### 6.7 No security headers (low)

Nothing sets `Content-Security-Policy`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy`, or `Cache-Control` for `index.html` (SPA shell must be
`no-cache`). Add them in the tunnel/nginx config or as an Axum layer.

### 6.8 Committed personal data (hygiene)

`scripts/import_export.py:24` hardcodes a personal email address and user UUID, and
references a gitignored `cloth_export_*.json`. Either scrub the identifiers and move
the script to a gitignored local path, or document it clearly as a one-off and
delete it after the import is done.

### 6.9 Discord token at cutover (process)

The old server's `.env` holds a live `DISCORD_BOT_TOKEN`. When the NUC takes over,
rotate or remove the old copy so the token isn't live in two places (the plan already
says this — make it a checklist item in §11 M6).

## 7. Reliability & operations

### 7.1 No health endpoint, no structured logging, no metrics

- No `/healthz` — the tunnel's health check and any uptime monitor have nothing to
  hit (both are specced in the plan and depend on this).
- All logging is `println!`/`eprintln!` with emojis; `src/main.rs:78-92` renders
  corrupted as `?? [Discord Sweep]` (emoji bytes didn't survive) — a signal that log
  output has never been viewed in a real environment.
- **Fix:** adopt `tracing` + `tracing-subscriber` (JSON or pretty), add
  `/healthz` (unauthenticated, pings `SELECT 1`), add a middleware that logs
  method/path/status/latency. Structured logs make the NUC `docker logs` actually
  usable.

### 7.2 `.unwrap()` on database results (medium)

`src/routes.rs` has 14 `.unwrap()`s on `fetch_all`/`fetch_optional` results (plus a
few in other handlers). A DB hiccup (pool exhaustion, lock timeout, transient
network) panics the request task: Axum returns 500 and the process survives, but the
failure mode is opaque and untestable. `db_write_error` already exists for the write
path — extend the same pattern to reads (`db_read_error` → 503 on transient
classification, 500 otherwise) and replace the unwraps.

### 7.3 `GET /tables` re-reads the schema on every call (minor perf)

`src/routes.rs:31-32` calls `state.schema.refresh(&state.db)` **per request** — the
exact per-request schema read the `SchemaCache` was built to eliminate (the CRUD
paths use the snapshot; the listing endpoint defeats it). Serve from the snapshot
and refresh on a TTL (e.g., 5 minutes) or an explicit `?refresh=1`.

### 7.4 Backups (process)

- Postgres: Supabase snapshots exist, but the plan's weekly `pg_dump` cron on the
  NUC (keep 4 weekly + 1 monthly, off-box rsync) should be installed **before**
  cutover, not after.
- Storage: uploaded photos have **no** independent backup. Add a weekly bucket export
  (Supabase Storage `list` + download, or `supabase storage` CLI) alongside the
  `pg_dump` cron.

### 7.5 Discord sync limitations (feature-adjacent)

- `fetch_messages(50)` — only the last 50 channel messages; no `before=` pagination
  back to the last already-reacted (`✅`) message. A busy channel silently drops
  older unimported outfits.
- Startup sweep fallback: when `DISCORD_DEFAULT_USER_ID` is unset,
  `src/main.rs:67-74` picks *the user with the most active clothing items* and
  imports their outfits. On a multi-user deployment this is a wrong-user hazard.
  Make `DISCORD_DEFAULT_USER_ID` required whenever Discord is enabled (fail startup
  loudly, or disable the sweep).
- `add_reaction` hand-URL-encodes two emojis (`✅`, `⚠️`) and passes any other emoji
  raw — fine for the two used, brittle if a third is ever added.

### 7.6 No graceful shutdown (minor)

`serve(listener, app)` with no signal handling — `SIGTERM` (docker stop) kills the
process mid-request. Trivial: register a tokio signal handler and call
`serve(...).into_make_service_with_connect_info(...)` shutdown, or axum's
`GracefulShutdown`.

### 7.7 Uptime monitoring (process)

Plan suggests Uptime Kuma on the NUC or a free external tier against `/healthz`.
Adopt at cutover (M6) — cheap insurance for a home NUC.

## 8. Testing & verification gaps

### 8.1 No integration tests — the biggest test gap (high leverage)

The backend's SQL is **rendered dynamically at startup** from the live schema
(`src/db.rs` builds `scoped_rows_sql`, `insert_sql`, `delete_sql`, `update_head/tail`
per table). The existing unit tests (`db.rs` `schema_tests`, `routes.rs` tests) verify
the *rendering rules* — but no test ever:

- applies the migration chain to a real Postgres,
- boots the app against it, and
- executes a real request against a real table.

A typo in a rendered statement, a column-type surprise, or a migration drift will
surface **only in production**. This is the single highest-leverage test investment
available, and it doubles as the proof that §5.1's base migration chain works.

**Work:** a CI job (or `cargo test --test integration` gated on a local Postgres
service container) that:
1. starts Postgres 16 (GitHub Actions service container),
2. applies `supabase/migrations/*.sql` in order (asserts the full chain, including the
   new base migration, runs clean),
3. seeds a fixture user + rows,
4. boots the app with a test `DATABASE_URL` / JWT secret,
5. exercises: 401 without token; 403 with wrong-role token; `/tables` listing;
   generic CRUD on a user-scoped table (insert forces `user_id`, PATCH/DELETE
   ownership, shared-table write forbidden); outfit create → wear_count increments,
   delete → decrements, item link integrity; `/upload` + `/files` ownership
   (own path OK, other user's path 404); settings round-trip (key stored encrypted,
   hint returned); `user-settings` blocked from generic API.

### 8.2 No frontend end-to-end tests

14 spec files cover the logic libraries well (dates/timezone, errors, router,
sanitize, undo, wardrobe store, picker, insights metrics/store, layout persistence,
widget smoke, `SettingsView`). Nothing drives the actual views.

**Work:** a Playwright suite (separate `frontend/e2e/`, not in the Vitest run) of the
five critical flows against `vite dev` + a stubbed Supabase auth + a stubbed backend
(both are thin HTTP, easy to mock):
1. login (email/password path),
2. list wardrobe + add item with image upload,
3. log an outfit (pick items, save) and verify the calendar day,
4. Insights tab renders with a seeded dataset (no console errors),
5. settings save + provider switch.

### 8.3 Try-on flow is untested on both sides

Both providers are thin HTTP calls behind `generate_outfit_preview`
(`src/routes.rs:1192`): Gemini REST and the local Qwen worker. Stub the two HTTP
endpoints (mock server in the integration suite, or a trait boundary) and test:
provider dispatch, missing-reference-photo 400, missing-api-key 400, item-not-in-
wardrobe 400, item-without-photo 400, image stored + thumbnails written, response
shape. Currently none of these paths is covered.

### 8.4 CI builds with placeholder env (low)

`ci.yml` deliberately builds the frontend with placeholder `VITE_SUPABASE_*` values
so CI stays green without secrets. Consequence: a build broken by an *empty*
production env would still pass. Add the guard described in §5.2 (assert the built
bundle contains the real URL when secrets are present).

### 8.5 No dependency-audit step (low)

Neither stack runs `cargo audit` / `npm audit` in CI. Cheap to add, catches the
occasional yanked/vulnerable dep before release.

## 9. Product feature gaps

Already present and working (for the record): item add/edit/deactivate with inline
reference-data creation, search + category filters, recency-sorted item picker,
outfit calendar with notes/photos/try-on, Discord import + link codes, 19 widgets
with global filters and keyboard/drag reorderable per-browser layout, undo for
destructive actions, deep links, truncation notices, connection test for local Qwen.

Gaps, in suggested priority:

### 9.1 Outfit editing (high value, medium effort)

There is **no `PATCH /outfits/:id`**. Once logged, an outfit's date, notes, items, or
photo cannot be changed — the only path is delete + recreate, which churns wear
counts (down then up) and breaks the "wear history" semantics. The transactional
patterns for create/delete already exist (`src/routes.rs:574-739`); an update is:
re-read outfit (scoped), diff item set, insert added links / delete removed links,
recompute affected `wear_count` deltas in one transaction. Add `updateOutfit` to
`client.ts` and an edit mode to `OutfitsView.vue`.

### 9.2 In-app export/import (high value for a personal app)

Data ownership: a "Export my wardrobe (JSON)" endpoint + import dialog. The one-off
`scripts/import_export.py` proves the JSON shape and idempotent SQL work, but it's a
manual script with hardcoded UUIDs and no UI. For a 1.0 personal app this is arguably
as important as the analytics. (Complements §5.1: with a reproducible schema, import
into a fresh project becomes the restore path.)

### 9.3 Reference-data management (medium value, low effort)

No way to **delete or rename** a color/category/subcategory/brand: creation
endpoints are add-only and the generic API forbids writes on shared tables. A
user who mistypes "Navay" is stuck forever (every item referencing it keeps the
stale slug). Add scoped delete/rename with FK re-pointing (or `ON DELETE SET NULL`
semantics for item references) and a small management UI in Settings or the item form.

### 9.4 Bulk item operations (low value, low effort)

Deactivate many at once, move many to a category, delete a batch. Quality of life.

### 9.5 Decide the multi-user story (affects §6.3, §7.5, §9.3)

- **Single-user** (the app is built for one wardrobe): state it explicitly in the
  README; §6.3 and §7.5's heuristic stop being concerns; §9.3 stays optional.
- **Multi-user** (any Supabase signup gets a wardrobe): §6.3 and §7.5 become
  blockers, and §9.3 becomes required (shared reference data per user).
The current code is *per-user correct* but *multi-user unsafe* in exactly those two
spots.

### 9.6 Polish (defer to 1.1 unless trivial)

PWA manifest / installability; offline tolerance for the wardrobe list; per-user
try-on defaults (seed, aspect ratio override); insights layout synced per *account*
instead of per *browser* (needs a settings table row — cheap given `user-settings`).

## 10. Code quality & maintainability

Mostly post-1.0, but listed so they can be picked up "in passing":

1. **`src/routes.rs` is 2,268 lines** mixing table CRUD, outfits, settings, Discord
   codes, try-on orchestration, upload, and file serving. Split into
   `routes/{tables,outfits,settings,discord,tryon,files}.rs` — mechanical, low-risk,
   and it makes every item in §6–§9 easier to do.
2. **Large single-file views:** `OutfitsView.vue` (1,832 L) and `SettingsView.vue`
   (1,247 L). Same story; optional.
3. **Dependency drift:** `rand 0.8` (with `#[allow(deprecated)]` in `crypto.rs` and a
   thread_rng that §6.2 wants replaced anyway), `axum 0.7` (1.x is stable),
   `dotenv` (vs `rusty_env`). Bumping `rand` is worth doing as part of §6.2; the rest
   can wait.
4. **Stale doc references:** comments in `routes.rs`/`db.rs` cite `UX_ANALYSIS.md`
   (deleted in commit `8e992c2`). Update or drop the references.
5. **README** is accurate and good; keep it in sync as §5/§9 land (endpoint table
   gains `/healthz`, outfit update, export/import; env table gains
   `CORS_ALLOWED_ORIGINS`).
6. **`local_inference/` is a separate deployment unit** (needs `sd-cli` on PATH,
   ~16 GB of GGUF weights, a 16 GB GPU — the worker comment even names the RX 9070
   XT). Keep it optional and documented, exclude from the main CI path, and consider a
   `Makefile`/`install.sh` that validates `sd-cli` presence (the worker already
   reports `sd_cli_found` in `/health`).
7. **`.cursorignore`** is 19 bytes (`/target/`-ish) — fine as is.
8. **`scripts/`** is a one-off migration tool — mark it as such in a README note or
   gitignore it after use (see §6.8).

## Closing assessment

The remaining work to 1.0.0 contains no new architecture and no risky rewrites. The
app's core — auth, scoping, data integrity, upload safety, transactions — is already
done to a high standard and is evidenced by tests. What separates the current state
from a 1.0.0 tag is:

1. **Reproducibility** — the schema must be clone-able and migration-runnable (§5.1).
2. **Reachability** — the app must be deployable to its real home without hand-holding
   (§5.2, M6).
3. **Trust** — the public-domain exposure items (§6), integration-level verification
   (§8), and honest release metadata (§5.3).

Execute M1–M7 in the order of §11 and the tag is earned.
