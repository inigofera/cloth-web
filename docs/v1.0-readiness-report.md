# cloth-web — Path to v1.0.0

Reviewed: 2026-11-19, branch `main` @ `06bc56a`. Scope: `src/` (Rust/Axum backend),
`frontend/` (Vue 3 + TS + Vite), `supabase/migrations/`, `infra/`, `local_inference/`,
`.github/workflows/ci.yml`, `docs/`, git history.

## 1. What the project is today

A personal wardrobe manager: clothing items with photos, an outfit logger (calendar),
a 19-widget analytics dashboard, generic table CRUD, AI virtual try-on (Gemini BYOK or
local Qwen/stable-diffusion.cpp), and optional Discord outfit-log import. Auth is
Supabase JWTs (HS256, `authenticated` role), data lives in Supabase Postgres + Storage.

**What's genuinely good (keep, don't re-litigate):**

- Per-user scoping done consistently: JWT extractor with role check, `user_id` forced on
  writes, `image_path` traversal validation, per-user storage keys, `/files` ownership gate.
- Upload pipeline is hardened: size cap, filename sanitization, magic-byte sniffing,
  EXIF orientation, 1600px downscale, thumbnail derivatives at upload time, bounded LRU
  image cache. Well-tested (`upload.rs`, `routes.rs` tests).
- Outfit create/delete are transactional with wear-count maintenance; item ids resolved
  server-side; no per-item round trips.
- SSRF validation on the local-Qwen URL (metadata IPs, reserved ports, loopback/LAN allowlist).
- Encrypted API keys (AES-256-GCM, nonce per write, never returned to client).
- Pagination + `X-Total-Count` honesty throughout; stable page ordering.
- CI runs fmt, clippy `-D warnings`, tests, release build for both stacks.
- Frontend has real unit tests (dates/timezone, errors, router, sanitize, undo, metrics,
  layout persistence), a11y work (listbox patterns, keyboard widget reordering),
  KeepAlive + deep links, 401→refresh retry in the fetch layer.

**Maturity assessment:** the *features* of a 1.0 are mostly present. What's missing is
the engineering scaffolding around them: reproducible schema, a deployment path,
integration-level tests, release hygiene, and a few security/ops hardening items.

## 2. Blockers (nothing is 1.0.0 without these)

### B1. The base schema is not in the repo
`supabase/migrations/` starts at `20260922…` and only adds constraints to an existing
`clothing-items` table. The tables the whole app depends on — `clothing-items`,
`outfits`, `outfit-items`, `brands`, `clothing-categories`, `clothing-subcategories`,
`colors` — were created manually in the Supabase project and **cannot be recreated
from this repo**. A fresh Supabase project (or a second instance, or a new machine)
cannot be brought up from `git clone`.

**Work:** write `20251001000000_base_schema.sql` (reconstruct columns from the app's
usage: `clothing-items` has `id uuid PK, user_id, name, brand_id, category_id,
subcategory_id, color_id, origin, laundry_impact, owned_since date, is_active,
wear_count, image_path, notes, created_at, updated_at`; `outfits` has
`id, user_id, date, notes, image_path, is_active, created_at, updated_at`;
`outfit-items (outfit_id, clothing_item_id)` with FKs + composite unique; reference
tables with their keys). Derive exact column lists from
`information_schema.columns` on the live project so the migration is byte-faithful.
Add RLS policies for all user-scoped tables (only `user-settings` has RLS today).
Then add the migration ledger (`schema_migrations` table + runner, per the home-infra
plan §1.6) so deployments apply migrations instead of manual psql.

### B2. Deployment path doesn't exist yet (the plan does)
`docs/home-infra-plan.md` (currently **untracked** — commit it) is a complete, sensible
plan: GitHub Pages frontend + Cloudflare Tunnel to the NUC, GHCR images, two CI jobs.
None of it is implemented:

- No `Dockerfile`, no compose file, no CI image/Pages jobs, no artifact handoff.
- No `CORS_ALLOWED_ORIGINS` / `axum-cors` — the backend has zero CORS support, so the
  planned cross-origin Pages↔API split will not work until this exists.
- No `/healthz` endpoint (tunnel/uptime checks have nothing to hit).
- `VITE_API_BASE_URL` is not read anywhere (`client.ts` hardcodes `/api`); the CI
  placeholder env means a production Pages build would ship with an empty Supabase URL
  and be a dead app.
- Cutover steps (DNS, tunnel, `.env` on the NUC, decommission old nginx, rotate the
  old server's Discord token) are all unstarted.

**Work:** execute the plan as written (its own estimate: ~2 days). It is the single
biggest chunk of the remaining effort.

### B3. Release hygiene
- Version strings are still `0.1.0` in both `Cargo.toml` and `package.json`.

## 3. Security hardening (do before the public domain goes live)

1. **Tokens in image URLs.** `imageUrl()` appends `?token=<JWT>` to every `/files`
   request, and the backend accepts `token` from the query string. Once the site is
   public, those JWTs will land in access logs (and possibly browser history /
   referrers). Options: short-lived signed image URLs, per-user cookie for `/files`,
   or at minimum stop logging query strings once the tunnel/proxy is in place.
2. **Discord link-code flow.** Codes are 6 digits from `rand::thread_rng()` (not
   CSPRNG) with no attempt limiting; the 15-minute window is guessable (~900k space)
   and a wrong code just gets a ❌ reply. Cheap fixes: `rand::rngs::OsRng`/`getrandom`,
   and rate-limit failed `!link` attempts per Discord user (e.g., 5 per hour) before
   revealing validity.
3. **Shared reference data is globally writable.** `POST /colors`,
   `/clothing-categories`, `/clothing-subcategories` write to *unscoped* tables, so any
   authenticated user can add (or, via the generic API? no — shared tables are
   write-forbidden there, so add-only) entries that appear in every user's UI. Fine for
   one user; wrong for a multi-user 1.0. Either scope reference data per user or gate
   creation behind a "you own the project" policy.
4. **JWT validation is secret+role only.** No `iss` check, so any token minted with the
   same Supabase secret from any project would pass. Add `validation.validate_iss`
   against `SUPABASE_URL` for a few lines of insurance.
5. **Schema mutation in code.** `connect_db()` runs
   `ALTER TABLE "user-settings" ADD COLUMN IF NOT EXISTS …` at startup. Move it into a
   migration (it duplicates `20261026…`); code should not write DDL in production.
6. **No rate limiting anywhere.** Upload (25 MB body cap), try-on generation (burns the
   user's Gemini quota / a 5-minute GPU), and the generic CRUD endpoints are all
   unlimited. At personal scale this is acceptable, but for a public deployment add at
   least per-user limits on `/upload` and `/outfits/generate-preview`.
7. **Security headers.** The frontend gets no CSP / `X-Content-Type-Options` /
   `Referrer-Policy` from nginx or the tunnel. Add a minimal set.
8. **Hygiene in committed files.** `scripts/import_export.py` hardcodes a personal
   email + user UUID; the file references a gitignored export. Either scrub or move
   out of the repo. The `scripts/` directory is a one-off migration tool — mark it
   as such or gitignore it after use.
9. **Discord token at cutover.** The old server's `.env` will still hold a live
   `DISCORD_BOT_TOKEN`; rotate or remove it when the NUC takes over (the plan already
   says this — just don't forget it).

## 4. Reliability & operations

1. **No health endpoint, no structured logging, no metrics.** Everything logs via
   `println!` (with an emoji-rendering artifact in `main.rs` — the "🔄/⚠" lines come
   out as `??`). Adopt `tracing` + a subscriber, add `/healthz` (DB ping), and consider
   a tiny request log. The home-infra plan's tunnel health check depends on `/healthz`.
2. **14 `.unwrap()`s in `routes.rs`** (plus more elsewhere) on database fetches — a
   DB hiccup panics the request task. Axum turns it into a 500, but a mapped error
   (`db_write_error`-style) is one-line-per-site work and removes the class of problem.
3. **`list_tables` refreshes the schema on every call** — the very per-request schema
   read the `SchemaCache` exists to eliminate (the cache is used for CRUD; the listing
   endpoint defeats it). Serve from the snapshot and refresh on a TTL or a query param.
4. **Backups.** Supabase snapshots exist, but the plan's weekly `pg_dump` cron on the
   NUC should actually be installed before cutover; storage objects (photos) have no
   independent backup — consider a weekly Supabase Storage bucket export.
5. **Discord sync limitations.** Only the last 50 messages are fetched (no pagination
   before an already-synced marker), and the startup sweep falls back to "the user with
   the most items" when `DISCORD_DEFAULT_USER_ID` is unset — a weird heuristic that will
   silently import the wrong user's outfits on a multi-user deployment. Make the env
   var required when Discord is enabled.
6. **No graceful shutdown / signal handling** — minor for this workload, but `Ctrl+C`
   on the NUC should stop the listener cleanly.
7. **Uptime monitoring** — the plan suggests Uptime Kuma; adopt it at cutover.

## 5. Testing & verification gaps

1. **No integration tests at all.** The backend's SQL is built dynamically at startup
   (`db.rs` renders insert/update/delete strings from the live schema); unit tests
   check the *rendering* of those strings, but nothing ever executes a real request
   against a real Postgres. A typo in a generated statement or a migration drift will
   only surface in production. Add a CI job that starts Postgres (service container or
   testcontainers-style step), applies all migrations from the repo (which doubles as
   the B1 test), and runs a set of end-to-end API tests: auth rejection, table CRUD,
   outfit create/delete wear-count invariants, upload + `/files` ownership, settings
   round-trip. This is the highest-leverage test investment available.
2. **Frontend has no e2e.** Unit tests cover the logic libraries well, but no test
   drives the actual views. A Playwright suite of the five critical flows (login,
   list/add item with upload, log outfit, insights renders, settings save) against a
   dev server + mock/sandbox Supabase would guard the UI for the release.
3. **Try-on flow is untested** on both sides (needs mocked Gemini/Qwen responses —
   both are thin HTTP calls, easy to stub).
4. **CI builds with placeholder Supabase env** for the frontend; fine for CI-green,
   but it means a broken production build env (empty `VITE_SUPABASE_URL`) would still
   pass. At minimum, add a check that the built bundle contains a non-placeholder URL
   when secrets are set.

## 6. Product feature gaps (decide in/out for 1.0)

Already present and working: item add/edit/deactivate + inline reference-data creation,
search/category filters, recency picker, outfit calendar with notes + photos +
try-on, Discord import, 19 widgets with keyboard reorderable layout, undo, deep
links, truncation notices.

Candidates to close before calling it 1.0 (roughly in priority order):

1. **Outfit editing.** There is no `PATCH /outfits/:id` — once an outfit is logged,
   its date, notes, items, and photo can't be fixed (delete + recreate is the only
   path, and that churns wear counts). The transactional patterns for
   create/delete already exist; the update is a straightforward addition.
2. **In-app backup/restore.** Data ownership for a personal app: a JSON export
   endpoint + import (the Python script proves the shape works, but it's a one-off
   with hardcoded UUIDs and no UI). Also the natural complement of B1's reproducible
   schema.
3. **Reference-data management.** No way to delete or rename a color/category/
   subcategory/brand (add-only endpoints; generic API forbids writes on shared
   tables). Users who mistype "Navay" are stuck forever.
4. **Item bulk actions** (deactivate many, move category) — quality of life.
5. **Multi-user story.** If 1.0 stays single-user, say so in the README and the items
   above (shared reference data, Discord sweep heuristic) stop being concerns. If 1.0
   means "any Supabase user can sign up and get a wardrobe," items 3 and the §3.3
   scoping become blockers.
6. **PWA manifest / installability, offline tolerance** — nice, not blocking.
7. **Settings: per-user try-on defaults** (seed, aspect override) — polish.

## 7. Code quality & maintainability (post-1.0 or in passing)

- `src/routes.rs` is 2,268 lines mixing table CRUD, outfits, settings, Discord codes,
  try-on orchestration, upload, and file serving. Split into `routes/{tables,outfits,
  settings,discord,tryon,files}.rs` — mechanical, low-risk, makes each of the above
  items easier to do.
- `OutfitsView.vue` (1,832 lines) and `SettingsView.vue` (1,247 lines) are large single
  files; same logic applies, optional.
- Dependency drift: `rand 0.8` (with `#[allow(deprecated)]` sprinkled in `crypto.rs`),
  `axum 0.7` (1.x is stable), `dotenv` vs `rusty_env`. Not 1.0-blockers; bump `rand`
  at least, since §3.2 wants `OsRng` cleanly.
- Stale doc references: comments cite `UX_ANALYSIS.md` which was deleted in
  `8e992c2`.
- `README.md` is accurate and good — keep it in sync as B1/B2 land (endpoint table
  will gain `/healthz`, outfit update, export/import).
- `local_inference/` is a separate deployment unit (needs `sd-cli`, ~16 GB of GGUF
  weights, a 16 GB GPU): keep it optional/documented, exclude from main CI, and pin
  the model filenames in the download script (it already does via env).

## 8. Suggested milestone order

| # | Milestone | Contents | Effort |
|---|-----------|----------|--------|
| M1 | Schema in repo | Base migration from live schema, RLS everywhere, ledger runner, commit `docs/` + pending changes | 0.5–1 day |
| M2 | Hardening | §3 items 1–6 (signed/cookie image tokens, OsRng + rate limit on link codes, `iss` check, move DDL to migration, upload/try-on limits, security headers) | 1 day |
| M3 | Ops readiness | `/healthz`, tracing, unwrap→mapped errors, `list_tables` from snapshot, graceful shutdown | 0.5 day |
| M4 | Integration tests | Postgres in CI + API e2e suite; frontend Playwright smoke of 5 flows | 1–2 days |
| M5 | Feature decisions | Outfit edit, JSON export/import, reference-data deletes (or explicitly defer with README note) | 1–2 days |
| M6 | Deployment | Execute `docs/home-infra-plan.md`: CORS, `VITE_API_BASE_URL`, Dockerfile, CI image + Pages jobs, compose, tunnel, DNS, cutover, backups, uptime, token rotation | ~2 days (plan's estimate) |
| M7 | Release | 1.0.0 in both manifests, CHANGELOG, LICENSE, tag `v1.0.0`, GitHub Release, README sync | 0.5 day |

**Critical path:** M1 → M2/M3 → M6 → M7. M4 and M5 can run in parallel with M2/M3.
Total: roughly **1.5–2.5 weeks** of focused work, with M6 being the longest single
stretch and the only one with external dependencies (Squarespace DNS, Cloudflare
account, NUC access).

**Verdict:** the application is functionally at "90% of 1.0." The remaining 10% is
almost entirely deployment, schema reproducibility, and verification — none of it
requires new architecture, and the repo's own `docs/home-infra-plan.md` already
specifies half of it.
